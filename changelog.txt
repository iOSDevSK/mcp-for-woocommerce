= Version 1.2.4 - Release #000019 - August 9, 2026 @ CET =

**SECURITY & WORDPRESS.ORG PLUGIN CHECK COMPLIANCE**

* #000034 - SECURITY: Validate client_id and redirect_uri on the OAuth authorization form submission
  Date: August 9, 2026
  - FIXED: `/mcpfowo/v1/auth/authorize-submit` accepted any `client_id` and `redirect_uri` from the POST body without checking them against a registered client. It then minted an authorization code bound to that URI and redirected the browser there with the code in the query string.
  - IMPACT: An attacker could host a form pointing at the endpoint with `redirect_uri` set to a host they control. An administrator who submitted credentials to it would hand over a valid authorization code, exchangeable for an access token. Open redirect plus authorization code leak.
  - CHANGED: Both `authorize()` and `authorize_submit()` now go through a shared `validate_client_redirect_uri()` check, which requires the client to be registered and the redirect_uri to match one of its registered URIs exactly. `authorize_submit()` validates before processing credentials.
  - NOTE: The `authorize()` endpoint already validated correctly; only the form submission path was affected.

* #000035 - Harden tax rate query and add caching
  Date: August 9, 2026
  - CHANGED: `wc_get_tax_rates` built its WHERE clause by concatenation and interpolated it into `$wpdb->prepare()`, which hid the placeholders from static analysis. Rewritten as a single literal query with every placeholder visible. The query was safe in practice; it is now verifiably so.
  - ADDED: Results are cached in the object cache for 5 minutes.

* #000036 - Serve the OAuth discovery document dynamically only
  Date: August 9, 2026
  - FIXED: `/.well-known/oauth-authorization-server` was served with a 404 status when no static file existed, because the handler runs on `template_redirect` after WordPress has already resolved the request as a 404. OAuth clients discard a 404. Now sends an explicit 200.
  - REMOVED: Activation no longer writes a static discovery file into the web root. It went stale when the site URL changed, and plugins should not write outside `wp-content`. Any file left by an earlier version is deleted on activation and deactivation.
  - FIXED: The discovery path is now matched against the parsed URL path, so a query string or trailing slash no longer breaks it.

* #000038 - Fix readme fields flagged by the WordPress.org importer
  Date: August 9, 2026
  - FIXED: `Contributors: filipdvoran` was ignored by the directory importer because no such WordPress.org user exists. Corrected to `webtalkbot`, the account that owns the plugin.
  - REMOVED: The Screenshots section listed four screenshots with no matching assets in the repository.
  - NOTE: The `Stable tag` pointed at 1.2.1, a tag that was never created in SVN, so the directory silently fell back to trunk. It now points at 1.2.4, which is tagged.

* #000037 - WordPress.org Plugin Check compliance
  Date: August 9, 2026
  - The distributed package now passes `wp plugin check` with zero errors and zero warnings.
  - REMOVED: `set_time_limit()` and `ini_set('memory_limit')` from `tools/list`.
  - REMOVED: `includes/Core/McpPhpProxy.php`, dead code duplicating the standalone CLI proxy.
  - CHANGED: Globally scoped functions renamed to the plugin prefix (`init_mcpfowo` to `mcpfowo_init_plugin`, `register_mcpfowo_cli_commands` to `mcpfowo_register_cli_commands`).
  - MOVED: `client-setup.md` to `documentation/client-setup.md`; the admin Documentation tab loads it from the new path.
  - REMOVED: `mcp-proxy.php` from the distributed package. It is a command-line script, so it cannot carry a direct-access guard and its STDERR writes cannot use WP_Filesystem. It remains available in the GitHub repository.
  - UPDATED: "Tested up to" is now 7.0 and lives only in readme.txt, so the two cannot disagree.

= Version 1.2.3 - Release #000018 - August 9, 2026 @ CET =

**BUGFIX: STREAMABLE HTTP TRANSPORT CORRUPTED EVERY JSON-RPC RESPONSE**

* #000031 - Fix unlabelled chunked-encoding framing on /wpmcp/streamable (GitHub issue #5)
  Date: August 9, 2026
  - FIXED: Every response from `/wp-json/wp/v2/wpmcp/streamable` arrived with HTTP chunk framing embedded in the JSON body (a hex length line before the payload and a trailing `0` chunk), so `json_decode()` and every spec-compliant MCP client failed to parse it.
  - ROOT CAUSE: The transport hand-wrote HTTP/1.1 chunked transfer-encoding framing into the response body and set the hop-by-hop `Transfer-Encoding: chunked` and `Connection: keep-alive` headers itself. Transfer encoding belongs to the web server / SAPI layer.
  - IMPACT: On nginx + PHP-FPM the FastCGI layer drops the hop-by-hop header and re-frames the body, so clients de-chunk one layer and are left with the application's framing bytes. HTTP/2 has no chunked encoding at all and fails the same way. Apache + mod_php happened to honour the header, which is why this went unnoticed.
  - CHANGED: The transport now returns a single, complete `application/json` body with a correct `Content-Length`, which is what the MCP Streamable HTTP transport specifies for a JSON response to a POST.
  - FIXED: Batches of more than 5 messages took a separate streaming code path that called `header('Mcp-Session-Id: ...')` after body output, so the session ID was silently dropped for any such batch containing `initialize`. Batches are now buffered and sent as one JSON array.
  - FIXED: Notification-only requests now return a genuinely empty `202` body instead of a stray `0\r\n\r\n`.
  - AFFECTED CLIENTS: Any backend MCP client relying on the transport spec, including `laravel/mcp`'s `WebClient` and the official MCP SDK `StreamableHTTPClientTransport`.

* #000032 - Remove references to the decommissioned demo host
  Date: August 9, 2026
  - FIXED: `docs/setup/claude-ai-connector-setup.md` pointed users at a demo endpoint that no longer exists; rewritten around `https://your-site.com` with auth, troubleshooting and verification steps.
  - CHANGED: `mcp-proxy.php` no longer hard-codes an endpoint. It now takes the URL from argv or the `MCPFOWO_URL` environment variable and exits with usage text if neither is given, so it can never silently point at somebody else's store.
  - FIXED: Connection logging recorded a hard-coded host instead of the actual site; now uses `home_url()`.

* #000033 - Add end-to-end transport tests
  Date: August 9, 2026
  - ADDED: `tests/e2e/` — raw-byte HTTP tests for the streamable endpoint, covering both the JWT and JWT-disabled proxy paths, plus a disposable nginx + PHP-FPM container stack. PHPUnit cannot cover this: the response emitter calls `exit()`, and Apache masks exactly the class of bug that issue #5 was.

= Version 1.2.2 - Release #000017 - April 22, 2026 @ CET =

**BUGFIX: JWT AUTH REST ROUTE COLLISION**

* #000030 - Fix "Unable to generate new token" error (GitHub issue #3)
  Date: April 22, 2026
  - FIXED: Token generation from admin UI no longer fails with "The username field is empty" error when the popular `jwt-authentication-for-wp-rest-api` plugin is also active.
  - ROOT CAUSE: Both plugins previously registered REST routes under the generic `jwt-auth/v1` namespace, causing the other plugin's handler to intercept our requests and reject them for missing credentials.
  - CHANGED: All auth REST routes moved from `jwt-auth/v1/*` to plugin-specific `mcpfowo/v1/auth/*` namespace (e.g. `/mcpfowo/v1/auth/token`, `/mcpfowo/v1/auth/tokens`, `/mcpfowo/v1/auth/revoke`, `/mcpfowo/v1/auth/register`, `/mcpfowo/v1/auth/authorize`, `/mcpfowo/v1/auth/authorize-submit`).
  - UPDATED: OAuth 2.0 discovery document now advertises the new endpoint URLs. MCP clients relying on discovery will pick up the change automatically on the next connect.
  - UPDATED: React admin UI now calls the new endpoint paths.
  - NOTE: External integrations that hard-coded `/wp-json/jwt-auth/v1/*` URLs must update them to `/wp-json/mcpfowo/v1/auth/*`.
